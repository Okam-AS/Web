# Brief — L-CORS-NARROW-THE-DEFAULT

## Objective
the deployed default names its origins instead of echoing whatever asks

**An earlier version of this lane text was wrong; read `F-PROD-BEARER-IS-SCRIPT-READABLE` first.** Production runs
`origin/master` and the permissive shape is `Program.cs:71-77` there — **but the identical default is also on the
integration branch** at `Program.cs:96-103` and on `lane/cors-followups` at
`Helpers/ServiceCollectionExtensions.cs:73-78`. **All three carry it.** The branches diverged at merge-base
`30dc54ae`, master +1 and integration +507, neither an ancestor of the other, so **a master-only fix is reverted the
day those commits merge** and will not conflict loudly. Name both targets.

**The part with no prior work behind it is the allowlist.** Nobody has checked whether narrowing the default breaks a
live caller — `okam-swiss.ch` is built from this same repo and points at the same API unless `API_BASE_URL` is
overridden at build time. Enumerating the live browser origins is the main event, not the tail.

**Do not push, do not deploy, do not touch production.** Read-only probes against live hosts are fine. The
deliverable is the diff plus a local proof, and the deploy is the owner's.

**The trap is specific and someone will hit it**: `AllowAnyOrigin()` with `AllowCredentials()` throws at
startup, and `SetIsOriginAllowed(_ => true).AllowCredentials()` does not. Do not produce the second one.

Note the ordering that makes 401s leak too — `UseCors` at `:210` runs before `UseAuthentication` at `:222`.

## Exit criteria
a diff against the production branch replaces the global permissive default with an enumerated origin list, and a preflight probe run against a locally hosted build shows a foreign origin refused where the deployed API admits it
