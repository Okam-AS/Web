## The design question: parse, or the lint rule

**The lint rule already exists, is already enabled, and already catches this. Nothing runs it.**

- `.eslintrc.js` extends `@nuxtjs/eslint-config-typescript`, and `npx eslint --print-config
  translations/no.ts` resolves `no-dupe-keys` to `["error"]`. Not switched off.
- Pointed at the reproduced merge result by hand it flags both keys, in 0.9 s:
  `line 3639 ... Duplicate key 'mrgs_err_projection_behind' (no-dupe-keys)`.
- But `package.json` has **no `lint` script**; neither `.github/workflows/claude.yml` nor
  `nuxtjs.yml` contains the string `lint`; and the husky **v4** hooks installed in `.git/hooks`
  read their hook map from a `husky` key in `package.json` **which does not exist**, so the
  configured `lint-staged` (`"*.{js,vue,ts}": "eslint"`) never fires on commit either.

So this is not the brief's `fail-spec` case ("a rule exists and is switched off"). It is the
adjacent one: an enabled rule wired into nothing — the same shape this program has already found
twice, a prover in no gate and a divergence comparison in no suite. Making it the gate would mean
introducing a lint step, and a first full-repo eslint run on this tree is a large unrelated cleanup
that would be switched off again.

**Chosen: a parse, wired into the jest suite.** `scripts/translation-duplicate-keys.js` parses each
dictionary with `typescript` (a *declared* dependency, `^4.7.4`, resolved 4.9.5 — not a transitive
`@babel/parser`) and walks **every `ObjectLiteralExpression` at every depth**, not the three files
and not lines. `test/translations-duplicate-keys.test.js` is what runs it, under the existing
`npm test`. A test cannot be turned off by editing a config file. `npm run check:translation-keys`
runs the same code standalone for a pre-merge check.

Line-counting was rejected and the rejection is asserted in the suite: a key inside a string body, a
commented-out key, a brace inside a template literal, and the same key in two *sibling* literals are
each a case a regex gets wrong, and each is a row in the table test.

## The falsification — reds on a real merge result, greens on the clean tip

`falsify.sh` drives it; full transcript in `falsify.txt`. Each merge result is regenerated by
`reproduce-merge.py <lane> <path> <out>` from the same three blobs the sibling's simulation used
(`git merge-file -p --diff3` of merge-base × `candidate/fe-compose-2026-08-05` × lane), so it is
re-runnable and not a stored fixture.

Every mutation is **asserted to have landed** before its result is read: files-changed = 1,
conflict markers = 0, occurrences of the key = 2, and `typescript` parses the result with 0 syntax
diagnostics — the merged file is *valid*, which is the whole point.

Two things in that table are worth saying out loud.

**The waste case is the proof.** On `translations/no.ts` carrying `mrgs_waste_err_quantity` twice,
**exactly one test in 2965 fails, and it is this one.** Nothing else in the suite notices. Without
this check that merge is completely silent.

**The money case is not a second success.** The other failing suite, `test/events-surface.test.js`,
fails for an unrelated reason: the merged `en.ts` carries **85 `ev_` keys that `no.ts` lacks**, which
that suite's parity assertion catches. It does not catch the duplicate — a parity test compares key
*sets*, and a set cannot represent a key that is present twice. So the existing parity coverage
(`translation-key-presence.test.js`, `events-surface.test.js`) is not this check in disguise.

**Read-only pass over the shared checkout's working tree** (the census's 47th claimant,
`/Users/svendaneel/okam/Web-modules`, dirty): 7 dictionaries, **duplicate keys: none** — 5129/5129/5164
keys against the tip's 5055/5055/5090. Nothing carries a duplicate today, which is why the check is
cheap now.

## An instrument correction inside this lane

The **first** run of `falsify.sh` recorded `Test Suites: 12 failed, 115 passed, 127 total / Tests: 2
failed, 2596 passed, 2596 total` under the money mutation. That number is **wrong and was
discarded.** The driver piped jest into `grep ... | head -12`; `head` closed the pipe, jest's
workers took SIGPIPE, and ten suites that ran fine were reported as failed while the test total came
out 369 short. The corrected driver writes jest output to a file and greps the file. The real number
is 2 failed suites / 2 failed tests / 2965 total. A truncating pipeline is not a measurement, and it
fails in the plausible direction: it *looks* like a stronger red.

## What this lane deliberately did not do

No duplicate was resolved and no sentence was picked. Nothing in the tree carries one, and the three
that the nine merges would introduce are an authoring judgement: two are money-facing and read in
opposite directions, one is a validation contract, and several strings in these dictionaries name
Norwegian statute on screen. The guard's failure message says which occurrence currently ships and
explicitly tells the reader **not** to delete one at random.
