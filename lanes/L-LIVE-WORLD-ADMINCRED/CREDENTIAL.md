## The three ways POST /User/login accepts a caller

`Controllers/UserController.cs:174-180`:

    verifiedDemoUser || verifiedPowerUser || await _userService.VerifyTokenAsync(user, model.Token)

The third is a real ASP.NET Identity phone token: generated by
`SendVerificationTokenAsync` (`Services/UserService.cs:560`), delivered by SMS, never knowable to a
test. And `GetOrCreateAsync` (`Services/UserService.cs:540`) puts any number that is neither of the
first two through a Twilio number lookup *before the account can exist at all*, so a journey cannot
even create such an account on a laptop.

**So a journey can only ever type one of the first two, and both are product settings rather than
fixture inventions** (`Services/UserService.cs:631-635`):

| | phone setting | code setting |
|---|---|---|
| the manager | `AppSettings:DemoPhoneNumber` | `AppSettings:DemoVerificationCode` |
| the PowerUser | `AppSettings:AdminUserPhoneNumber` | `AppSettings:PowerUserVerificationCode` |

## Why the manager cannot be this journey's subject

`test/e2e/scripts/live-world.sh` registers the store through `POST /Stores/register` **under the
demo manager's own bearer**, and `StoreService.RegisterAsync` writes the caller's own `StoreAdmins`
row. The script asserts that row exists before it proceeds. So in every world that script builds the
demo manager **is** a store admin, which is the exact opposite of what this journey needs.

## The PowerUser bypass, and the environment variable

`appsettings.json:13` ships

    "AdminUserPhoneNumber": "Set in Azure. For development, set in User Secrets"

and `Helpers/ServiceCollectionExtensions.cs:182` narrows Identity's account-name charset to
`+0123456789`. `Services/PowerUserRoleSeed.cs:67-80` therefore refuses that placeholder outright and
logs at **Critical** that nobody will ever hold PowerUserRole. **The bypass is inert out of the
box.** There is no committed number, no number in the estate's docs, and none should be written
down: an operator picks one and hands it to the API process as

    AppSettings__AdminUserPhoneNumber=+47XXXXXXXX

in the exact `+47`-prefixed form the account is registered with (the login modal prefixes `+47`
itself, so the journey types only the national part). The code half is
`AppSettings:PowerUserVerificationCode`, which does have a committed value in the API's own
`appsettings.json` — named here, deliberately not quoted, because copying a bypass code into a
second repo buys nothing.

## The substitution is not neutral, and a live artifact must say so

`adminIn` is computed purely from `StoreAdmins` rows and never consults the role
(`Services/StoreService.cs:177`), so the bypass account **does** resolve to `worker` in the shell and
every refusal the journey asserts is genuinely observed. All three declared capabilities survive.

But signing in on that number **grants PowerUserRole** — `Services/UserService.cs:601` calls
`PowerUserRoleSeed.EnsureConfiguredAdminHoldsRoleAsync` at token-issue time precisely so the grant
cannot depend on deploy ordering — and `StoreAdminAuthorizationHandler:17` succeeds on that role
alone, with no membership.

**So a live run of this journey shows the browser shell refusing an account the API itself would
admit.** That is a sharper fact than the fixture's and a different one. The fixture's `+4790000001`
is a plain worker; the live subject is the platform administrator. An artifact from a live run must
not be read as "a worker was refused by the backend".

## What this lane changed, and what it proved

One file, `test/e2e/journeys/admin-refusal-worker.spec.js`:

1. The record above, in the journey's header, with file:line.
2. `E2E_WORKER_PHONE` / `E2E_WORKER_CODE`, defaulting to today's fixture pair.
3. The `@fixture` tag comes off **only** when `E2E_WORKER_PHONE` is set. `@fixture` means "depends on
   state only the fixture has", and the fixture-only state this journey depends on is exactly the
   worker's phone number. Live selection is byte-for-byte unchanged until somebody supplies one.
   `live-world.sh`'s header calls un-tagging a journey before its world exists "the one outcome worse
   than having no live run at all"; a conditional tag cannot do that.
4. The number is kept **out** of the artifact when it came from the environment — only its source is
   written (`env:E2E_WORKER_PHONE`). It is an operator's personal phone number and journey records
   get pasted into reviews.
5. Step 1 asserted the premise in **prose** and checked nothing: it returned the literal
   `'signed in as +4790000001, adminIn: []'`. It now reads `adminIn` off the persisted Vuex state the
   way `utils/admin/nav-access.js` does, and distinguishes an empty list from an **absent** field —
   which is the `unknown` state the shell deliberately does not refuse on, and which would otherwise
   have passed as a zero.

## What is NOT done: the live run

The journey did **not** run live, and this lane could not make it.

A live world needs a SQL Server, and this host has SQL Server only in containers. Five are up
(`okam-lws-sql`, `okam-lws-staff-sql`, `okam-lwr-sql`, `okam-lvsp-sql`, `zen_pasteur`) and **none is
this lane's**; `live-world.sh` borrows one and `DROP`s/`CREATE`s a catalog on it. This lane is
`class: node` with no container slot, and its brief forbids both starting a container and touching
one it did not create. Three of those containers are holding worlds standing on purpose for Sven's
acceptance walks (`F-ACCEPTANCE-IS-THE-CHOKE`), so taking one is not a cheap mistake.

Re-using a standing world does not work either, for a reason that is the finding itself: the
credential is an **environment variable on the API process**. None of the four `WebApi` processes now
listening (`:5091`, `:5951`, `:5952`, `:5956`, `:5961`) was started with
`AppSettings__AdminUserPhoneNumber`, so making one of them serve this journey means restarting
another lane's API — or standing a new one against their catalog, which writes an `ApplicationUser`
row into their world.

**This is where the brief mis-sizes the lane.** It calls this "the last of the three groups, and the
smallest: one credential", `class: node`, `pts: 1`. The credential alone is not enough: because the
live half of it is a process-level environment variable and not a value, the journey cannot go live
without a world **built for it**. That is a `class: sql` act, the same one `L-LIVE-WORLD-STAFF`
(`class: sql`, `pts: 2`) was given a slot for.

    E2E_WORKER_PHONE=<national part of that number> E2E_WORKER_CODE=<AppSettings:PowerUserVerificationCode> \
        npm run test:e2e -- test/e2e/journeys/admin-refusal-worker.spec.js

**And it must record, in whatever it returns, that the live subject held PowerUserRole** — otherwise
the artifact claims a worker refusal that the run did not observe.

workforce journeys it does not consume the week and can share a world.
