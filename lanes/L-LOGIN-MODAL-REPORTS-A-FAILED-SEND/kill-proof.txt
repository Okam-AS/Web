--- WHICH LAYER WAS FIXED, AND WHY -------------------------------------------------------------
THE MODAL, not the request layer. The brief is right that the resolve is the deeper cause, but:

  • `RequestService.PostRequest` resolving a failed request is a DOCUMENTED, DEPENDED-ON contract.
    Its own source says so, and the `SafeGetRequest` / `SafePutRequest` / `SafeDeleteRequest`
    variants exist for the sole purpose of making the other verbs behave the SAME way — "PostRequest
    already behaves this way" is a comment in that file. `TryParseResponseWithError` unwraps the
    axios error deliberately.
  • 205 call sites read a request result through `TryParseResponse` / `TryParseResponseWithError`.
    Making PostRequest reject turns every one of those `false` returns into an unhandled rejection.
  • The honest boolean was ALREADY on the signature the modal called:
    `SendVerificationToken(phoneNumber): Promise<boolean>`. Three of its four callers already read
    it — core/pinia/user.ts:150, pages/registrer.vue:573, components/molecules/EmployeeManager.vue:177.
    LoginModal was the only one that threw the value away.

So this is a caller bug, not a layer bug, and the brief's own warning — "the next caller will make
the same assumption" — is already answered by the typed boolean the layer returns. The request layer
was NOT touched. Neither was test/e2e/support/admin.js, which 31 journeys share.
