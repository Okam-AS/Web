WHAT I FOUND THAT THE BRIEF DID NOT SAY (and that contradicts the note in the two specs)
    03  journey A -> journey B with NO reset PASSES. The documented collision ("each begins by
        needing the current week unplanned") does not red in that direction: once the previous
        revision is PUBLISHED the draft view resolves no revision, so the page badge reads
        "Ingen plan", "Opprett utkast" is offered, and journey B creates *Revisjon 2*.
        It does not fail — it produces weaker evidence than its header claims, about a week that
        had already been planned and published. Compare 03 (Revisjon 2) with 05 (Revisjon 1).
        The real one-directional collision is the FLAG, not the week (06).

C1 — A RESTORE IS NOT AN UNPICK
    No UPDATE and no DELETE anywhere in live-world-reset.sh, against a guarded table or any other.
    The catalog is replaced whole, from an image, by the engine.
    Every reset verifies the guards came back: all 25 non-shipped triggers present, none disabled,
    and a SHA2_256 over (name | parent table | is_disabled | full body) identical to the image's —
    1235fd1c1036754f43b512ac1ae880601dc718e5917072dc36e03e05dac87214 — on every one of the resets
    logged here.
    `snapshot` refuses a world that already carries a revision, a publication or a flag override,
    so the image can never become a way to rewind a world somebody wrote a real answer into.

C7 — the image never leaves the container. /var/opt/mssql/backup/OkamLiveRestore.livesnapshot.bak
    (10 MB) and its manifest live inside okam-lwr-sql; the script refuses any path outside
    /var/opt/mssql/. Nothing was docker cp'd out and nothing of the sort is committed.

C2 — no migration authored. The chain on the branch is applied by live-world.sh and replayed only
    when a world is built from empty.
